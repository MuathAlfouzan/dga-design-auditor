DGA Auditor Handbook

Score any website or Figma design against Saudi Arabia's national design system, out of 100, with a per-check breakdown you can act on. The engine runs inside the page and writes nothing to disk.

What it does

It measures a real page against the real standard. Every colour, typeface, size, spacing value, radius, shadow and contrast ratio that actually reached the screen is compared against tokens extracted from SDGA's own Figma files — then scored against a fixed rubric of 28 checks.

The same target scores the same twice. That is the whole premise: 22 of the 28 checks are computed from measured data with no judgement involved, and the six that need eyes are recorded with a stated count rather than an impression.

Four ways to run it

Ordered by how much you need installed. The first needs nothing at all.

In any browser

Needs nothing — no install, no account

Open the page you want to score, open the console with ⌥⌘J, and paste:

const src = await (await fetch('https://cdn.jsdelivr.net/gh/MuathAlfouzan/dga-design-auditor@main/dist/dga-rate.js')).text();
(0, eval)(src);
__dga.audit({ label: 'desktop' });
__dga.overlay();

The scorecard renders over the page. Resize to phone width and call audit again to add the mobile half. This is the one to hand a colleague, and the one that gets past WAFs — it is just your browser making an ordinary request.

As a library

Needs Node 18+ and the repo

import { score, scoreByViewport, explain, inlineReport } from './src/score.js';
import { renderScorecard, renderSplitScorecard } from './src/render.js';

The core is pure — no filesystem, no network, no DOM. It takes captures and a ledger and returns a verdict, which is why it runs identically in Node and in a browser.

How the score works

Three parts, 28 checks, 100 points

PartPointsCoversBacked by
Foundations58Colour tokens, type ramp, spacing and radius scales, elevation, motionthe Foundations file
Components24Component anatomy, variants, states, icon set, official marksComponents Library + Icons
Standards18RTL and bilingual behaviour, WCAG accessibilityDGA guidance, not a library

Each part is normalised to 100 within its own weight, so Foundations 66 and Components 57 are directly comparable — 40/58 and 12/24 are not. Standards is its own part because folding accessibility into Components would misattribute a contrast failure to a button.

Web and mobile are scored separately

Target sizes and container widths belong to a viewport, not to a site. A page can pass at 1440 and fail at 390, and averaging the two produces a figure describing neither. There is no blended score.

The site-level overall takes the worst viewport, per part as well as in total. An average would let a strong desktop hide a failing phone.

Bands, and the government gate

BandScore
Compliant90–100
Substantially compliant75–89
Partial60–74
Non-compliantunder 60
Four checks are blockers — C2 off-palette brand colour, I2 mark misuse, A1 text contrast, A2 non-text contrast. They must be fully met, not 90% met: one text run below 4.5:1 means the page does not conform. A failed blocker holds the band at Partial however high the number climbs. The number itself is never adjusted — the band carries the gate, and the report names what capped it.

A check that cannot apply leaves the denominator

It is never counted as a failure. A Figma frame has no focus rings; a page with no dark theme has no dark tokens to check. Those checks report n/a and the score is out of what remained. Every report states how many of the 28 were graded.

Asking why, and how to fix

Every answer has the same shape — what was lost, why, and what recovers it — sorted by points recoverable, because "fix this and gain 5" is actionable where "this failed" is not.

__dga.explain()                       // every part, worst first
__dga.explain({ part: 'components' }) // points lost, and what recovers them
__dga.explain({ check: 'T1' })        // what was found vs expected, and the fix

In conversation, ask it in words: "why did the components score drop?", "what's the cheapest way to gain 10 points?", "what's failing on mobile that passes on desktop?"

On a split, answers come back per viewport — the same question can have different answers at 1440 and 390, which is the point of scoring them apart.

Keeping it current

A score is only as good as the baseline behind it, so every report states ledger.synced and the DGA release it was extracted against. No network call is needed for that.

Whether something newer exists is a separate check, against two sources that do different jobs: DGA's changelog gives the system version, and each Figma file's ---- Updates ---- block says what changed in that file. Neither can be read without a browser — the changelog is a client-rendered app and Figma returns 403 to anything that is not a browser.

Figma fileStatusLast published
Foundationssynced2025-07-02
Components Librarysynced2025-11-03
Mobile Componentssyncednever amended
Iconsdeferred2026-01-11

Icons is deferred deliberately. Its own update log carries a DGA notice dated 11 January 2026 saying the icon library is being rewritten and icons may be temporarily unavailable — syncing it now would capture a library in flux. While it is deferred, the icon check scores n/a rather than being guessed at.

What it refuses to do

These are deliberate. A compliance tool that produces a confident wrong number is worse than one that stops.

  • Score against an unsynced ledger. A made-up baseline produces a made-up number, so it errors instead.
  • Judge a check with no baseline. With Icons unsynced there is no size scale to measure against, so the icon check reports n/a rather than an impression. Same for mark usage, which has no identity baseline.
  • Score a blocked page. A WAF rejection page will score perfectly happily — Times New Roman on white, one blue link — and that number describes a page nobody designed.
  • Blend two viewports. Covered above, and it is enforced in the data: a split carries no combined score field at all.
  • Invent a token. Where the Figma files are silent, the gap is recorded and the affected check drops out. The ledger lists what is missing.
  • Silently drop the judged checks. Scoring refuses if a judged check was never assessed, because quietly omitting the component checks is how a rebuild scores as compliant.

Known gaps

Recorded in the ledger rather than papered over, because a gap you can see is worth more than one you cannot.

  • No dark-mode token set exists in any DGA file, so the dark-theme check is always n/a.
  • No motion tokens are published, so the motion-token check is n/a.
  • No minimum target size is published anywhere in the system. The accessibility check uses the WCAG 2.2 floor of 24px, labelled in the ledger as WCAG's number and not DGA's.
  • The Display md ramp step is missing — the ramp runs 60, 48, ?, 30, 24. No file emitted it, so it was not invented.
  • Page templates are not yet synced, so component checks compare against component specs without a page-level reference.
Two traps caught during extraction, and excluded. Shopify Polaris variables left in a documentation page — including one carrying Polaris's own misspelling — and the green and red "do and avoid" annotation swatches from the guidance frames. Admitting either would have taught the auditor that an off-brand grey, or the colour used to mean correct in a diagram, is compliant.
